# ADR-0004: PostgreSQL y persistencia

- **Estado:** propuesta
- **Fecha:** 2026-10-20
- **Responsable:** Pendiente de asignación

## Contexto

**Hechos comprobados**

- `backend/pom.xml` declara Spring Data JPA y el driver PostgreSQL en runtime; Java está configurado en 25 y Spring Boot en 4.1.1.
- `backend/src/main/resources/application.properties` obtiene la URL JDBC mediante `DB_URL`, configura `spring.jpa.hibernate.ddl-auto=validate`, desactiva Open Session in View y `show-sql`. El backend ahora contiene entidades JPA y repositorios funcionales para los dominios implementados.
- `backend/src/main/resources/db/schema.sql` contiene definiciones para `usuario`, `proveedor`, `servicio`, `recurso`, `agenda`, `horario_disponible`, `reserva` y `evento_auditoria`, además de claves, restricciones e índices.
- El mismo SQL incluye `ENABLE ROW LEVEL SECURITY` para esas tablas y comentarios que describen el uso previsto con Supabase. No contiene instrucciones `CREATE POLICY`; esto solo describe el archivo local y no confirma las políticas actuales del proyecto remoto.
- No hay Flyway ni Liquibase declarados en el POM. `backend/src/main/resources/db/migration/` contiene `.gitkeep` y un subdirectorio `manual/` con una guía y una migración SQL no versionada; `backend/src/main/resources/db/migrations/` también contiene un SQL manual. Spring Boot no ejecuta automáticamente esos scripts.
- `schema.sql` usa `GENERATED ALWAYS AS IDENTITY` para varias claves y `GENERATED BY DEFAULT AS IDENTITY` en `servicio`. La compatibilidad del esquema remoto con el archivo local no fue verificada desde una conexión a Supabase.

El problema es definir cómo se mantiene la compatibilidad entre el esquema PostgreSQL y el modelo Java, y cómo se introducen cambios de esquema con seguridad. La configuración `validate` verifica mapeos cuando existan; no crea tablas ni constituye por sí sola una estrategia de migración.

## Alternativas consideradas

Estas alternativas se comparan para esta propuesta; no se afirma que hayan sido evaluadas previamente por el equipo.

1. **Mantener el esquema SQL como contrato y Hibernate en modo `validate`.** Evita que el ORM cambie el esquema automáticamente; requiere gestionar los cambios de forma separada.
2. **Usar una herramienta versionada de migraciones (por ejemplo, Flyway o Liquibase).** Proporciona historial y ejecución ordenada de cambios, pero requiere seleccionar, configurar y operar una herramienta.
3. **Permitir que Hibernate cree o actualice el esquema automáticamente.** Puede simplificar entornos desechables, pero no es la configuración actual y puede producir cambios no revisados sobre una base persistente.

## Decisión

**Decisión propuesta, pendiente de aprobación:** mantener los nombres y restricciones del esquema PostgreSQL como contrato de persistencia y conservar `spring.jpa.hibernate.ddl-auto=validate`. No cambiar a `update`, `create` o `create-drop` para una base compartida o persistente. No seleccionar aún Flyway, Liquibase ni otro mecanismo: acordar primero una estrategia de migraciones y verificarla con el equipo y el estado real de Supabase.

Esta propuesta no afirma que el esquema local sea idéntico al remoto ni prescribe políticas RLS. Las políticas, grants, propiedad de tablas y rol JDBC deben investigarse antes de definir acceso de aplicación.

## Consecuencias

- Positivas:
  - Evita que Hibernate altere automáticamente el esquema persistente.
  - Hace explícito que los mapeos Java deben corresponder a tablas y columnas existentes.
  - Mantiene separada la validación de mapeo de la evolución del esquema.
- Negativas / riesgos:
  - Sin mecanismo de migraciones aprobado, los cambios de base de datos no tienen todavía historial reproducible en el repositorio.
  - Una diferencia entre el SQL local y Supabase puede impedir el arranque o generar comportamientos distintos.
  - Habilitar RLS sin conocer políticas y rol de conexión puede bloquear operaciones o dar una impresión incorrecta de aislamiento.
  - El archivo local contiene valores JDBC configurados directamente en propiedades de conexión; no se reproducen aquí. Debe revisarse su gestión y evitar exponer secretos.
- Impacto en calidad, seguridad, pruebas y despliegue:
  - Los futuros mapeos deben probarse contra PostgreSQL y el modo `validate`.
  - Los cambios de esquema requieren revisión de compatibilidad, preservación de datos y mecanismo de despliegue aprobado.
  - La política RLS debe probarse con los roles reales de la API/backend; el acceso como propietario puede tener semántica diferente.
